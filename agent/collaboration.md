## 1. 역할과 경계

### 1.1 한 문장 원칙

> **경계는 [`contract.md`](./contract.md) 하나다.** 그 문서 안쪽은 공동 책임, 바깥쪽은 각자 재량이다.

계약을 지키면 서로의 코드를 몰라도 된다. 이 구조가 유지되는 동안 두 팀은 **병렬로 일할 수 있다.**

### 1.2 소유권

| 영역 | 프론트 | 에이전트 | 비고 |
|---|---|---|---|

| `MockTransport` · 목 스크립트 | **소유** | 참고 | 에이전트 팀은 이걸 **행동 참고 자료**로 본다 (`spec.md` 6.6) |

### 1.3 서로에게 요구할 수 있는 것

| 프론트 → 에이전트 | 에이전트 → 프론트 |
|---|---|

| 한국어 카피 톤 준수 | 카피 톤 리뷰 |
| 종료 이벤트 보장 | 목 폴백 경로 유지 |
| `traceId` 로깅 | 개발 모드에서 `traceId` 노출 |

### 1.4 서로에게 요구할 수 없는 것

| 요구 | 왜 안 되는가 |
|---|---|
| 프론트 → "특정 LLM·프레임워크를 써라" | 계약 밖이다. 결과만 보면 된다 |
| 프론트 → "도구를 이 이름으로 나눠라" | `behavior.md`의 도구 목록은 **권고**다 |
| 에이전트 → "이 필드는 안 보내도 되게 화면을 바꿔라" | 화면 요구가 곧 필드 요구다. 바꾸려면 `spec.md`부터 |
| 에이전트 → "계약 테스트를 느슨하게 해라" | 실패는 프론트가 깨진다는 뜻이다. 테스트를 고치지 말고 원인을 고친다 |
| 양쪽 → "일단 이렇게 보낼게" (통보 없이) | 계약 변경은 §2 절차를 따른다 |

## 2. 인터페이스 소유권과 변경 절차

### 2.1 왜 절차가 필요한가

계약이 조용히 바뀌면 상대는 **런타임에** 알게 된다. 발표 전날 화면이 깨지는 가장 흔한 원인이다.

### 2.2 변경 유형별 절차

| 유형 | 예 | 절차 |
|---|---|---|
| **호환 유지** (minor) | 선택 필드 추가, 열거값 추가, 문구 수정 | PR + 상대 팀 **알림**. 승인 없이 머지 가능 |
| **호환 파괴** (major) | 필드 제거·이름 변경·필수화, 이벤트 타입 변경, 불변식 추가 | PR + **양측 승인 필수** + [ADR 작성](#8-의사결정-기록adr) |
| **문서 정리** | 오타, 설명 보강, 표 정리 | 자유 |

### 2.3 계약 변경 PR 체크리스트

`contract.md`를 건드리는 PR에 그대로 붙여 쓴다.

```
□ 변경 유형: minor / major
□ 왜 필요한가 (한 문장)
□ 대안을 검토했는가 (계약을 안 바꾸고 해결할 방법)
□ 영향받는 작업: cityInfo / flightSearch / staySearch / placeDiscovery / itineraryGenerate / itineraryVerify
□ 영향받는 화면 (spec.md 화면 ID: S0~S9)
□ contract.md 버전을 올렸다 (§11.1 규칙)
□ schemas/*.json을 함께 수정했다
□ fixtures/를 함께 수정했다
□ tools/conformance.mjs의 검사를 함께 수정했다
□ 양쪽 구현 중 어느 쪽이 먼저 배포되어도 깨지지 않는가 (배포 순서 의존성)
□ major면: 상대 팀 승인 + ADR 링크
```

**"양쪽 중 어느 쪽이 먼저 배포되어도 깨지지 않는가"** 가 가장 중요하다. 동시 배포는 불가능하므로, 변경을 **두 단계로 쪼개는 것**이 안전하다.

```
필드 이름을 a → b로 바꾸고 싶다면

1단계  서버가 a와 b를 둘 다 보낸다 (b 추가, minor)
2단계  프론트가 b를 읽도록 바꾼다
3단계  서버가 a를 뺀다 (major, 하지만 이제 아무도 안 읽는다)
```

### 2.4 계약 위반 발견 시

```
1. 계약 테스트를 돌려 재현한다
   node agent/tools/conformance.mjs <baseUrl> <task>
2. 실패 ID(예: I-V2, L1.12)와 함께 이슈를 만든다
3. contract.md의 해당 절을 링크한다
4. 계약이 틀렸다면 §2.2 절차로 계약을 고친다
   구현이 틀렸다면 구현을 고친다
```

⛔ **계약 테스트를 통과시키려고 테스트를 수정하지 않는다.** 테스트가 잘못됐다고 판단되면 그 근거를 이슈에 적고 합의한 뒤 고친다.

## 3. 저장소와 PR

### 3.1 저장소 구조 🔶

두 가지 안이 있다. 킥오프에서 정한다. → [§7-11](#7-결정-대기-목록)

| 안 | 구조 | 장점 | 단점 |
|---|---|---|---|
| **A. 단일 저장소** (권장) | `2026_KNUxKU_summer_camp_team01/` 안에 `voyagent/`(프론트) + `agent-server/`(에이전트) | 계약 문서가 한 곳. 계약 변경 PR에서 양쪽을 동시에 수정할 수 있다. 캠프 규모에 적합 | 언어가 섞인다(TS + Python) |
| B. 분리 저장소 | 프론트 · 에이전트 각각 | CI·의존성이 깔끔 | `agent/` 문서를 복사·서브모듈로 동기화해야 한다. **버전 어긋남이 실제로 일어난다** |

> A를 권한다. 캠프 기간에 두 저장소의 계약 문서를 동기화하는 비용이 언어 혼재의 불편보다 크다.

### 3.2 브랜치

```
main                    항상 동작하는 상태
feat/agent-place-discovery
feat/agent-verify-rules
fix/contract-timezone
docs/contract-v1.1
```

### 3.3 PR 규칙

| 항목 | 규칙 |
|---|---|
| 제목 | `[FE]` / `[AGENT]` / `[CONTRACT]` 접두 |
| 크기 | 리뷰 가능한 크기로. 계약 변경은 **반드시 별도 PR** |
| 리뷰어 | 계약 변경 = 양쪽 각 1명. 그 외 = 같은 영역 1명 |
| 머지 조건 | 계약 테스트 통과 (에이전트) / `typecheck` + `lint` + `test` 통과 (프론트) |
| 계약 변경 PR | §2.3 체크리스트를 본문에 붙인다 |

### 3.4 커밋 메시지


## 4. 동기화 리듬

캠프 기간에는 문서보다 **짧은 대화**가 빠르다. 다만 결정은 반드시 문서에 남긴다.

| 주기 | 형식 | 내용 |
|---|---|---|
| **매일 (10분)** | 스탠드업 | 어제 한 것 / 오늘 할 것 / 막힌 것. **계약 관련 이슈가 있으면 여기서 먼저 말한다** |
| **주 2회 (30분)** | 통합 세션 | 프론트 + 에이전트를 실제로 붙여서 한 흐름을 끝까지 돌려본다 |
| **마일스톤 종료 시** | 리뷰 (30분) | [§5 DoD](#5-definition-of-done) 확인 + [`behavior.md` §7 루브릭](./behavior.md#72-루브릭) 채점 |
| **수시** | 이슈 / 채팅 | 계약 위반 발견 시 즉시 |

### 4.1 통합 세션에서 하는 일

```
1. NEXT_PUBLIC_AGENT_MODE=live + 해당 작업 플래그로 프론트를 띄운다
2. 골든 케이스 G1을 처음부터 끝까지 돌린다 (S0 → S7)
3. 화면을 함께 본다. 에이전트 팀이 자기 출력이 어떻게 렌더되는지 직접 본다
4. 이상한 곳을 그 자리에서 이슈로 만든다
5. 루브릭 5축을 채점한다
```

> **에이전트 개발자가 자기 출력이 렌더된 화면을 직접 보는 것**이 이 세션의 핵심이다. JSON만 보면 `summary`가 60자를 넘는지, `agentNote`가 노이즈인지 알 수 없다.

### 4.2 이슈 라벨

| 라벨 | 의미 |
|---|---|
| `contract` | 계약 변경 제안·논의 |
| `contract-violation` | 계약 위반 버그. **최우선** |
| `agent-quality` | 형식은 맞지만 결과가 나쁨 ([`integration.md` §9.3](./integration.md#93-계약-테스트가-통과하는데-화면이-이상할-때)) |
| `blocked` | 상대 팀 결정 대기 |
| `decision-needed` | [§7](#7-결정-대기-목록)에 올려야 하는 항목 |

## 5. Definition of Done

### 5.1 에이전트 작업 1개

작업 하나가 "끝났다"의 정의. 하나라도 빠지면 끝나지 않았다.

```
계약
□ node agent/tools/conformance.mjs <baseUrl> <task> 통과 (실패 0)
□ 경고가 있으면 이유를 이슈나 코드 주석에 남겼다
□ 종료 이벤트가 모든 경로(성공·실패·타임아웃·취소)에서 보장된다
□ 출력 직전 불변식 검사 계층이 있다 (behavior.md 1.6절 [3])

행동
□ 골든 케이스 5개(G1~G5) 전부 실행 후 오류 없음
□ behavior.md 7.2절 루브릭 5축 전부 3점 이상
□ 추론 문장에 사용자 입력이 인용된다
□ freeNote가 있으면 반영하고 언급한다
□ 한국어 카피가 길이 상한 안에 있다

통합
□ 프론트에서 실제 화면을 확인했다 (JSON만 보고 끝내지 않았다)
□ 실패 경로를 확인했다 (no_results, timeout)
□ 취소 시 LLM 호출이 실제로 멈춘다

관측
□ 실행 1건 = 로그 1줄이 남는다
□ traceId가 요청·로그에 이어진다
```

### 5.2 마일스톤

```
□ 해당 마일스톤의 모든 작업이 §5.1을 통과
□ 통합 세션에서 전체 흐름(S0→S7)을 한 번 완주
□ 목 폴백이 여전히 동작 (플래그를 끄면 즉시 목으로 돌아간다)
□ contract.md에 변경이 있었다면 버전을 올리고 양측이 확인
□ 결정 대기 목록(§7)에서 해당 마일스톤 항목이 정리됨
```

### 5.3 계약 문서

```
□ 🔶 제안 항목이 ✅ 확정 또는 삭제로 정리됐다
□ 부록 A의 정합성 메모가 spec.md에 반영됐거나 "반영 안 함" 결정이 기록됐다
□ schemas/ · fixtures/ · tools/가 문서와 일치한다
□ 버전이 v1.0-draft → v1.0으로 올라갔다
```

## 6. 마일스톤

`spec.md` 14.1의 26단계와 병렬로 진행한다. 프론트 9단계(에이전트 계층)가 끝나면 계약면이 열린다.

|---|---|---|---|---|
| **M0** | 계약 합의 + 스텁 서버 | 6개 작업이 계약을 지키는 이벤트를 낸다. 내용은 목 데이터 그대로 | 없음 (병렬 가능) | 계약 테스트 6개 전부 통과 |

| **M2** | `itineraryGenerate` | 배치 알고리즘 + 이동시간 | `spec.md` 16단계(일정 생성) | §5.1 |
| **M3** | `itineraryVerify` | 규칙 엔진 V1–V10 + 서술 + 자동 수정 | `spec.md` 21단계(S7 검증 UI) | §5.1 + 규칙 일치 테스트 |
| **M4** | `cityInfo` · `flightSearch` · `staySearch` | 웹 조사·출처 + 필터·순위·태그 | `spec.md` 11·13단계 및 도시 정보 사용처 | §5.1 |

### 6.1 M0을 먼저 하는 이유

M0의 스텁 서버는 **결과 품질이 0점이지만 계약은 100점**이다. 이게 있으면

| 효과 | 설명 |
|---|---|
| 프론트가 즉시 live 경로를 검증할 수 있다 | `SseTransport`·프록시·SSE 버퍼링 문제를 미리 잡는다 |
| 전송 계층 버그와 품질 문제가 섞이지 않는다 | M1 이후 문제가 생기면 원인이 오케스트레이션이라고 확정할 수 있다 |
| 계약의 애매한 부분이 드러난다 | 문서로 읽을 때는 안 보이던 구멍이 구현하면 보인다 |

> M0은 하루면 된다. 이걸 건너뛰고 M1부터 시작하면 **전송 문제와 품질 문제를 동시에 디버깅**하게 된다.

### 6.2 최소 데모 경로

시간이 부족할 때 반드시 살려야 하는 것. `spec.md` 14.3과 맞춘다.

```
M0 → M1(placeDiscovery) → M2(itineraryGenerate) → M3(itineraryVerify)
```

`flightSearch`·`staySearch`는 페르소나에서 "아니요"를 선택해 우회한다. 이 경로만으로도 **"페르소나 → 장소 발견 → 일정 생성 → 검증"** 이라는 제품의 핵심 서사가 완성된다.

⛔ 반대로 `flightSearch`부터 시작하면 가장 우회 가능한 것에 시간을 쓰게 된다.

## 8. 의사결정 기록(ADR)

계약을 파괴적으로 바꾸거나 되돌리기 어려운 선택을 할 때만 쓴다. 캠프 기간에 5개를 넘기면 과하다.

`agent/adr/{번호}-{제목}.md`

```markdown
# ADR 001 · 검증 규칙 판정을 에이전트 서버로 옮긴다

- 상태: 채택 (2026-08-20)
- 결정자: 프론트 @이름 · 에이전트 @이름

## 맥락
spec.md 9장은 규칙 V1~V10을 프론트(src/lib/verify/rules.ts)에 두도록 설계됐다.
목 모드에서는 백엔드가 없으므로 그래야 했다. live 모드에서는 판정 근거와
자연어 서술이 함께 나와야 자연스럽고, 판정 로직이 프론트에 있으면 서술만
서버에서 만들어야 해서 근거와 문장이 어긋난다.

## 결정
live 모드에서는 에이전트 서버가 판정한다. 프론트 구현은 참조 구현으로 남기고,
같은 입력으로 양쪽을 돌려 severity가 일치하는지 비교하는 테스트를 둔다.

## 대안과 기각 이유
- 프론트가 계속 판정하고 서버는 서술만: 근거와 문장이 어긋난다. 서버가 판정
  결과를 입력으로 받아야 하는데 그러면 왕복이 두 번이다.
- 규칙 로직을 공용 패키지로 추출: 언어가 다르면(TS vs Python) 불가능하다.

## 결과
- 프론트 rules.ts는 mock 모드 전용 + 참조 구현으로 유지
- integration.md 5.3절에 규칙 일치 테스트 추가
- 두 구현이 갈리면 spec.md 9.2를 기준으로 판정
```

## 9. 리스크와 대응

| 3 | **LLM이 계산을 틀린다** | 검증 결과가 이상하다 | 계산은 결정론적 코드로 ([`behavior.md` §1.6](./behavior.md#16-llm과-결정론적-코드의-경계)) |

| 5 | **발표 중 LLM 장애·쿼터 초과** | — | 응답 캐시 + 목 폴백 + 리허설 3회 ([`integration.md` §8.4](./integration.md#84-데모-준비)) |

| 7 | **결과 품질이 목보다 나쁘다** | 통합 세션에서 "목이 더 낫네" | 루브릭으로 조기에 측정. 3점 미만이면 릴리스하지 않는다 |

| 10 | **양쪽이 서로를 기다린다** | 스탠드업에서 `blocked`가 반복 | 결정 대기 목록(§7)에 올리고 기한을 정한다. 기한이 지나면 기본 제안으로 진행 |

### 9.1 가장 위험한 것

> **리스크 4 (`Place.id` 불일치)** 가 가장 조용하고 가장 늦게 터진다.

계약 테스트로 잡히지 않고, 단일 작업 테스트로도 안 보인다. **S5에서 고른 장소가 S6에서 사라지거나, 공유 링크를 열었을 때 이름만 나오는** 형태로 나타난다. 발견 시점이 늦으면 목 데이터 전체를 다시 만들어야 한다.

M1 착수 전부터 [`behavior.md` §1.5](./behavior.md#15-데이터-소스와-id-안정성)의 매핑 규칙과 공용 snapshot 회귀 검사를 적용한다.
