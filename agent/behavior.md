## 1. 공통 요구사항

### 1.1 추론 노출 원칙

이 제품의 두 번째 핵심 가치는 **"AI 작업을 눈으로 보여준다"** 다 (`spec.md` 1.2). 추론 스트림은 로딩 화면의 장식이 아니라 **기능**이다.

| 원칙 | 내용 | 나쁜 예 | 좋은 예 |
|---|---|---|---|
| **결정을 말한다** | 무엇을 했는지가 아니라 **무엇을 왜 골랐는지** | `데이터를 조회하고 있습니다` | `늦은 밤 도착은 첫날 일정을 줄이므로 감점했어요` |
| **입력을 되읽는다** | 사용자가 준 조건을 그대로 인용해 "내 말을 들었구나"를 만든다 | `조건에 맞는 항공편을 찾습니다` | `직항만, 오전 출발 선호, 1인 90만원 이하. 이 조건에 맞는 항공편만 남깁니다` |
| **제외 이유를 말한다** | 뺀 것을 말하면 남긴 것이 신뢰를 얻는다 | (침묵) | `유아차 이용을 고려해 계단이 많은 곳은 뒤로 미뤘어요` |
| **숫자를 준다** | 막연한 서술보다 구체적 수치 | `여러 곳을 확인했습니다` | `312곳을 수집해 86곳으로 좁혔어요` |
| **거짓을 만들지 않는다** | 실제로 하지 않은 판단을 문장으로 꾸며내지 않는다 | 도구를 안 썼는데 `실시간 가격을 확인했어요` | 한 일만 말한다 |

**추론 문장의 위치** — `spec.md` 6.6의 스크립트가 좋은 참고다. 모든 작업이 같은 리듬을 따른다.

```
1. 입력 요약        "무엇을 찾을지 이해했다"
2. 수집 결과 규모   "많이 봤다"
3. 필터 근거        "왜 좁혔다"
4. 순위 근거        "왜 이 순서다"
5. 결론 + 특이사항  "이게 결과이고 이건 알아둬야 한다"
```

⛔ **금지**

- 도구 호출을 그대로 나열하기 (`search_flights를 호출합니다` → 도구 카드가 이미 보여준다)
- 내부 구현 노출 (`GPT-4o에게 프롬프트를 전달합니다`, `LangGraph 노드 실행 중`)
- 사과·양해 (`죄송하지만`, `잠시만 기다려 주세요`)
- 사용자에게 되묻기 (스트림은 단방향이다. 응답할 방법이 없다)

### 1.2 한국어 카피 규칙

에이전트가 보내는 모든 문자열은 **디자인 검수를 거치지 않고 화면에 그대로 박힌다.** `spec.md` 7장의 카피 톤과 어긋나면 그 화면만 어색해진다.

**어체**

| 필드 | 어체 | 예 |
|---|---|---|
| `status` | `~고 있어요` (현재 진행) | `항공권을 찾고 있어요` |
| `thought` | `~합니다` / `~했어요` (서술) | `이 조건에 맞는 항공편만 남깁니다` · `감점했어요` |
| `tool_call.label` | `~중` (명사형 진행) | `항공편 데이터베이스 조회 중` |
| `tool_result.label` | 명사형 결과 | `128개 항공편 확인` |
| `done.summary` | `~어요` + 추천 한 줄 | `12개 항공권을 찾았어요. 추천은 대한항공 684,000원입니다.` |
| `agentNote` / `agentReason` | `~어요` (친근) | `유아차 이동이 편해 가족 여행 첫날에 적합해요` |
| `issue.title` | `~니다` (사실 진술) | `도쿄 국립박물관이 방문일에 휴관입니다` |
| `issue.detail` | `~니다` | `이 박물관은 매주 월요일 휴관입니다.` |
| `autoFix.summary` | `~기` (동작 명사형) | `Day 3(6/14 토) 10:30으로 옮기기` |
| `check.message` | 명사형 또는 `~어요` | `3개 장소 중 1건 휴관일 충돌` |
| `evidence` | 명사형 단문 | `영업시간: 화–일 09:30–17:00, 월요일 휴관` |

**길이 상한** — 넘으면 말줄임되거나 레이아웃이 밀린다.

| 필드 | 상한 | 잘리는 위치 |
|---|---|---|
| `status.text` | 20자 | 패널 헤더 |
| `tool_call.label` | 20자 | 도구 카드 2행 |
| `tool_result.label` | 20자 | 도구 카드 3행 |
| `thought.text` (문장 1개) | 120자 | 초과 시 새 `id`로 분리 |
| `done.summary` | 60자 | 결과 요약 바 1행 |
| `Place.summary` | 90자 | 리스트 4행 (2줄 말줄임) |
| `Place.description` | 400자 | 드로어 (4줄 후 더보기) |
| `agentNote` · `agentReason` | 40자 | 카드 1행 |
| `Itinerary.agentSummary` | 60자 | 결과 요약 바 |
| `agentHighlights[]` | 40자 × 3–4개 | 불릿 |
| `ItineraryDay.title` | 20자 | 일자 헤더 인라인 |
| `issue.title` | 40자 | 이슈 카드 제목 |
| `issue.detail` | 120자 | 이슈 카드 본문 |
| `autoFix.summary` | 40자 | 제안 카드 |
| `autoFix.impact` | 20자 | `이동시간 +4분` |
| `evidence[]` | 60자 × 2–4개 | 근거 불릿 |
| `check.message` | 40자 | 체크리스트 2행 |

**숫자 표기** — `spec.md` 8.9를 따른다. 프론트가 재포맷하지 않는 자유 문장에서는 **서버가 직접 지켜야 한다.**

| 대상 | 형식 | 예 |
|---|---|---|
| 금액 (KRW) | 천 단위 콤마 + `원` | `684,000원` |
| 금액 (외화) | 통화 기호 + 콤마 | `¥2,100` · `€24` · `฿350` |
| 시각 | 24시간 `HH:mm` | `15:00` |
| 소요 시간 | 60분 미만 `{n}분` / 이상 `{h}시간 {m}분` / 분이 0이면 `{h}시간` | `45분` · `1시간 30분` · `2시간` |
| 날짜 (짧게) | `M/D 요일` | `6/12 목` |
| 날짜 (길게) | `M월 D일 요일` | `6월 12일 목요일` |
| 기간 | `{n}박 {n+1}일` | `4박 5일` |
| 거리 | 1km 미만 `{n}m`(10m 단위) / 이상 `{n.n}km` | `840m` · `1.2km` |
| 평점 (5점) | 소수 1자리 | `4.5` |
| 평점 (10점) | 소수 1자리 | `8.7` |
| 일자 참조 | `Day {n}` (1부터) + 필요하면 날짜 병기 | `Day 3(6/14 토)` |

> `dayIndex`는 0부터지만 **사용자에게 보이는 표기는 `Day 1`부터**다. `dayIndex: 2` → `Day 3`. 오프바이원을 자주 틀리는 지점이다.

**⛔ 금지** ([`contract.md` §7.6](./contract.md#76-텍스트-) 재확인)

마크다운 · HTML · 이모지 · 개행 · 영문 예외 메시지 · 내부 식별자 노출(`tokyo-sensoji` 대신 `센소지`)

### 1.3 페르소나 반영 규칙

`Persona`는 6개 작업 중 3개(`placeDiscovery`, `itineraryGenerate`, `itineraryVerify`)에 통째로 전달된다. **어떤 필드가 무엇을 바꿔야 하는지**를 명시한다. 이걸 무시하면 페르소나 설문(S2) 전체가 무의미해진다.

| 필드 | 반영해야 하는 곳 | 반영 방법 |
|---|---|---|
| `interests` | `placeDiscovery` 선별·정렬 | 각 관심사를 최소 1건 우선 커버하고 상위 관심사는 3건까지. 매칭 항목을 배열 앞으로. `interestTags`로 표시 |
| `pace` | `itineraryGenerate` 하루 밀도 | `PACE_CONFIG`의 `placesPerDay`·`startTime`·`endTime` 준수 (§5.2) |
| `companionType` | 장소 선별 톤, `agentNote` | `family`면 아이 동반 적합성, `couple`이면 분위기, `colleagues`면 접근성·효율 |
| `travelers.children` + `childAges` | 장소 선별, 체류 시간 | 유아 동반 시 체류 시간 단축, 계단·장거리 도보 감점 |
| `travelers.seniors` | 같음 | 도보 이동 감점, 휴식 블록 |
| `travelers.pets` | 장소 선별 | 반려동물 불가 실내 시설 감점 |
| `accessibility.longWalkOk: false` | `itineraryGenerate` 동선 | 하루 도보 합계 3km 이하 목표. V7이 초과를 잡는다 |
| `accessibility.stroller` / `wheelchair` | 장소 선별 · 클러스터링 | `accessibility` 필드가 `false`인 곳 감점(제외는 아니다) |
| `accessibility.avoidStairs` | 같음 | `manyStairs: true` 감점 |
| `budget` | `placeDiscovery` 유료 비중, `itineraryGenerate` 배치 | 예산이 낮으면 무료·저가 장소 비중을 높인다 |
| `transports` | `itineraryGenerate` 이동 수단 | `TravelLeg.mode` 선택. `car` 없으면 택시·도보·대중교통만 |
| `freeNote` | 전부 | **자유 텍스트를 프롬프트에 그대로 전달한다.** 반영했으면 `thought`에서 언급 |

**`freeNote`를 반영했음을 보여준다** 🔶

사용자가 `아이가 라멘을 좋아해요. 비 오는 날 갈 만한 실내 장소도 알려주세요`라고 썼다면, 추론 문장에 반드시 등장해야 한다.

```
"메모에 적어주신 라멘을 반영해 아사쿠사와 신주쿠의 라멘집을 후보에 넣었어요.
 6월 장마를 고려해 실내 장소도 함께 골랐습니다."
```

> 이것이 이 제품에서 **사용자가 가장 감동하는 순간**이다. 자유 입력을 무시하면 설문 마지막 문항이 장식이 된다.

### 1.4 결정론과 시드

| 항목 | 규칙 |
|---|---|
| E2E 테스트 | 프론트는 `MOCK_SEED`로 목 스트림을 고정한다. live 모드에서는 **결정론을 요구하지 않는다** |
| 계약 테스트 | 형식·불변식만 검사하므로 결과가 매번 달라도 통과해야 한다 |
| 권고 | LLM `temperature`를 낮게(0–0.3) 두면 디버깅과 데모가 훨씬 쉽다 |
| 데모 안정성 | 발표 직전에는 **응답 캐시**를 켜는 것을 권한다. 같은 입력 → 같은 결과 → 리허설이 의미를 갖는다 |

### 1.5 데이터 소스와 ID 안정성

✅ **결정** — live 후보 수집은 Google Places, 테스트·데모·장애 폴백은 버전이 고정된 공용 스냅샷을 사용한다.

| 문제 | 프론트 fixture와 live API가 서로 다른 `Place.id`를 만들면 공유 링크와 진행 중인 여행이 깨진다 |
|---|---|
| ID 규칙 | Google Place ID를 내부 매핑 키로 보관하고, 외부 계약에는 안정적인 `{cityId}-{정규화된 영문 slug}`를 사용한다. 충돌 시 매핑 테이블에 고정 suffix를 저장한다 |
| live 모드 | Google Places API에서 후보를 수집하고 정규화·필터·순위화해 최대 20건 반환한다 |
| fixture 모드 | 4개 도시 공용 JSON 스냅샷을 사용한다. 계약 테스트와 E2E에서 결과를 재현하는 기준 데이터다 |
| fallback | API 장애·rate limit 시 같은 스냅샷으로 전환하되, live 응답과 fixture를 한 결과 배열에 섞지 않는다 |
| 공유 링크 방어 | 프론트가 `placeId` 조회 실패 시 이름·시각만 표시하도록 설계한다 (`spec.md` S8) |

스냅샷은 live 데이터 소스를 대체하는 별도 정책이 아니라 **fixture·cache·fallback**이다. 양측이 임의로 다른 JSON을 만들지 않고 같은 버전을 참조한다.

> 이 구조에서도 에이전트의 가치는 온전하다. **어떤 20곳을 고르고, 어떤 순서로 두고, 왜 그런지 말하는 것**이 이 제품의 차별점이고, 그건 데이터 출처와 무관하다.

### 1.6 LLM과 결정론적 코드의 경계

가장 자주 틀리는 설계 판단이다. **계산을 LLM에게 맡기면 신뢰가 무너진다.**

| 이것은 결정론적 코드로 | 이것은 LLM으로 |
|---|---|
| 거리·이동시간 계산 (haversine + 계수, `spec.md` 15.2) | 왜 이 순서인지 서술 |
| 영업시간 대조 (요일 인덱스 비교) | 휴관일 문제를 사람 말로 설명 |
| 가격 합산·예산 비교 | 예산 초과에 대한 조언 |
| 시각 산술 (`startTime + duration`) | 하루 테마 제목 (`아사쿠사 & 스카이트리`) |
| 검증 규칙 V1–V10 판정 | 판정 결과의 근거 문장·자동 수정 제안의 이유 |
| 정렬·필터·집계 | 장소 소개문·추천 이유(`agentNote`) |
| 카테고리 균형 확인 | 페르소나 적합도 판단 |
| 불변식 검사 (출력 직전) | 자유 입력(`freeNote`) 해석 |

**왜 이렇게 나누는가**

> V1이 "6월 15일은 월요일"을 틀리면 검증 기능 전체의 신뢰가 사라진다. 날짜 계산은 LLM이 할 일이 아니다.
> 반대로 "월요일 휴관이라 Day 3으로 옮기면 우에노 공원과 같은 지역이라 이동이 늘지 않아요"는 코드가 쓸 수 없는 문장이다.

**권고 구조**

```
사용자 입력
   ↓
[1] 결정론 계층 — 필터·계산·정렬·판정
   ↓  구조화된 중간 결과 (숫자와 사실)
[2] LLM 계층 — 중간 결과를 근거로 서술·선별 이유·제안 생성
   ↓
[3] 검증 계층 — 불변식 검사 (contract.md §5의 I-* 항목)
   ↓
이벤트 스트림
```

[3]을 **반드시 둔다.** LLM이 만든 필드가 열거형을 벗어나거나 존재하지 않는 `placeId`를 참조하는 일은 실제로 자주 일어난다. 출력 직전에 스스로 검사해서 걸러내면 프론트가 깨지지 않는다.

## 2. `flightSearch`

### 2.1 목표

사용자 조건에 맞는 **왕복 묶음 후보를 최대 20건** 제시하고, 왜 추천하는지 근거를 붙인다. 실제 검색 결과가 20건보다 적으면 조건을 완화하거나 결과를 부풀리지 않고 확보한 후보만 반환한다.

기본 데이터 소스는 [Amadeus Self-Service Flight Offers Search API](https://developers.amadeus.com/self-service/apis-docs/guides/developer-guides/resources/flights/)로 정한다. API 응답은 Tool 계층에서 `FlightOffer`로 정규화하며, API 키가 준비되기 전에는 fixture를 사용한다.

### 2.2 판단 기준

**필터 (하드 조건)** — `FlightSurvey`

| 조건 | 처리 |
|---|---|
| `nonstopOnly: true` | 직항만 |
| `maxLayoverMinutes` | 초과 경유 제외 |
| `outboundWindows` / `inboundWindows` | 비어 있으면 **무관**(전부 통과). ⛔ 빈 배열을 "아무것도 통과 안 함"으로 해석하지 않는다 |
| `preferredAirlines` | 비어 있으면 무관. 값이 있으면 **가점**(하드 제외 아님) |
| `excludedAirlines` | 하드 제외 |
| `cabinClass` | 해당 등급만 |
| `maxPrice` | 1인당 상한 초과 제외 |

> **필터가 결과를 0건으로 만들면** `error`(`no_results`)를 보내고, `message`에 **어느 조건이 원인인지** 담는다. 프론트가 `[그 필터 해제]` 버튼을 만들 수 있다.
> 예: `직항 조건 때문에 결과가 없어요. 경유를 허용하면 3개를 찾을 수 있어요`

**순위 (소프트 점수)** 🔶

| 요소 | 가중 | 근거 |
|---|---|---|
| 가격 | 높음 | 1인당 가격의 역수 정규화 |
| 총 소요시간 | 높음 | 경유 대기 포함 |
| **도착 시각의 일정 영향** | 높음 | 이 제품만의 관점 — 아래 참조 |
| 선호 항공사 일치 | 중간 | `preferredAirlines` |
| 출발 시간대 일치 | 중간 | `outboundWindows` |
| 환불 가능 · 수하물 | 낮음 | — |

**"도착 시각의 일정 영향"이 이 에이전트의 차별점이다.** `spec.md` 6.6.1:

> *"가격과 소요시간, 도착 시각이 일정에 주는 영향을 함께 봅니다. 늦은 밤 도착은 첫날 일정을 줄이므로 감점했어요."*

| 도착 시각 | 첫날 가용 시간 | 점수 |
|---|---|---|
| 06:00–11:00 | 거의 온전 | 가점 |
| 11:00–15:00 | 오후 반나절 | 중립 |
| 15:00–19:00 | 저녁만 | 소폭 감점 |
| 19:00 이후 | 첫날 소실 | 감점 |

출발편도 대칭으로 판단한다(이른 오전 출발은 마지막날을 잃는다).

### 2.3 태그 부여

| 태그 | 조건 | 개수 |
|---|---|---|
| `recommended` | 종합 점수 1위 | 정확히 1 |
| `cheapest` | `price.amount` 최소 | 정확히 1 |
| `fastest` | 총 소요시간 최소 | 정확히 1 |
| `nonstop` | `stops === 0` | 다수 허용 |
| `best-value` | 가격/시간 파레토 최적 | 0–2 |

한 오퍼가 여러 태그를 가질 수 있다. 프론트는 좌상단에 우선순위 1개만 표시한다.

### 2.4 도구 구성 제안

| 도구 | `label` | `resultLabel` |
|---|---|---|
| `search_flights` | 항공편 데이터베이스 조회 중 | `{n}개 항공편 확인` |
| `apply_constraints` | 조건 필터 적용 중 | `{n}개 항공편이 조건을 통과` |
| `rank_offers` | 추천 순위 계산 중 | `상위 {n}개 선별` |

### 2.5 `agentNote`

**추천 상위 3건에만** 붙인다. 전부에 붙이면 아무 의미가 없다.

| 좋은 예 | 나쁜 예 |
|---|---|
| `오전 도착이라 첫날 일정을 넉넉하게 쓸 수 있어요` | `좋은 항공편입니다` |
| `경유 1시간 40분이지만 가격이 27만원 저렴해요` | `가성비가 좋습니다` |
| `밤 도착이라 첫날은 이동과 체크인만 가능해요` | `늦게 도착합니다` |

## 3. `staySearch`

### 3.1 목표

**위치가 결정적**인 선택을 돕는다. 가격만 나열하면 이 화면은 예약 사이트와 다를 게 없다. 기본 데이터 소스는 Google Maps Platform의 Places API이며, 실시간 객실 가격·예약 가능 여부는 범위에 포함하지 않는다. 계약을 만족하는 후보를 최대 20건 반환한다.

Places API는 숙소의 정적 정보·평점·위치를 담당한다. `nightlyPrice`, `totalPrice`, 취소 정책은 팀이 관리하는 데모 가격 fixture에서 가져온 **예상값**이며 예약 가능성을 의미하지 않는다. `rooms`는 재고 필터가 아니라 예상 총액 계산 배수로만 사용한다. 실제 예약 링크나 “예약 가능” 문구를 만들지 않는다.

### 3.2 판단 기준

**필터** — `StaySurvey`

| 조건 | 처리 |
|---|---|
| `types` | 비어 있으면 전체 |
| `nightlyBudget` | 데모 fixture의 예상 1박 가격 `{min, max}` 범위. `null`이면 무관 |
| `minRating` | `reviewScore` 하한 (10점 척도) |
| `amenities` | **하드 조건.** "꼭 있어야 하는 것"이라고 물었다 |
| `rooms` | 재고 확인에 쓰지 않는다. `totalPrice` 계산 시 객실 수 배수로 사용 |
| `bedPreference` | `any`면 무관 |

**순위** 🔶

| 요소 | 가중 | 조건 |
|---|---|---|
| `placesCentroid`까지 거리 | **최상** | 입력에 있을 때만 |
| `locationPriority` 일치 | 높음 | `downtown` / `nearStation` / `nearAttractions` / `quiet` |
| 가격 | 높음 | 예산 범위 내 낮은 쪽 |
| `reviewScore` | 중간 | — |
| `cancellation: 'free'` | 낮음 | — |
| `arrivalTime`과 체크인 정합 | 낮음 | `considerFlightArrival: true`일 때 |

**`placesCentroid`를 반드시 쓴다** — `spec.md` 6.6.2:

> *"선택하신 가고 싶은 곳 {n}곳의 중심을 계산했어요. 이 지점에서 가까운 숙소에 가중치를 줍니다."*

이 값이 있으면 `distanceToPlacesKm`를 채우고(I-S6), 추론 문장에서 언급한다. 프론트의 정렬 옵션 `가고 싶은 곳에서 가까운순`이 이 필드에 의존한다.

### 3.3 위치 요약은 필수 정보다

`distanceSummary`(`신주쿠역 도보 6분`)는 **지도를 쓸 수 없는 사용자의 유일한 위치 정보**다. `spec.md` S4 접근성 요건:

> *"지도를 쓸 수 없는 경우를 위해 카드에 위치 정보(`distanceSummary`)가 항상 텍스트로 존재"*

빈 문자열로 두면 접근성 요건 위반이다.

### 3.4 태그 부여

| 태그 | 조건 |
|---|---|
| `best-location` | 위치 점수 1위 |
| `best-value` | 가격/평점 비 1위 |
| `recommended` | 종합 1위 |
| `top-rated` | `reviewScore` 최고 |

### 3.5 도구 구성 제안

| 도구 | `label` | `resultLabel` |
|---|---|---|
| `search_stays` | 숙소 데이터베이스 조회 중 | `{n}곳 확인` |
| `score_by_location` | 위치 점수 계산 중 | `역세권 {n}곳 우선` |
| `apply_constraints` | 조건 필터 적용 중 | `{n}곳이 조건 충족` |

### 3.6 리뷰 요약

`reviewQuotes`는 **실제 리뷰에서 발췌**한다. 없으면 빈 배열로 둔다.

⛔ 리뷰를 창작하지 않는다 (`spec.md` 3.14.3 "존재하지 않는 후기 금지"). 데이터에 리뷰가 없으면 프론트가 그 섹션을 다른 구조로 렌더한다.

`reviewHighlights`는 `청결도`/`위치`/`시설`/`가격` 4개 고정(I-S7). 원본 데이터에 항목이 없으면 계산 가능한 것만 채우지 말고 **4개를 모두 채우거나 빈 배열로** 둔다. 2개만 오면 게이지 4행이 깨진다.

## 4. `placeDiscovery`

### 4.1 목표

Google Maps Platform의 Places API 후보 중 최대 20곳을 **페르소나 기준으로 큐레이션**한다. 이 작업의 출력이 일정 생성의 입력이므로, 품질이 뒤 화면 전체를 좌우한다.

### 4.2 선별 기준

```
전체 후보
  → [1] 도시 필터
  → [2] 관심사 매칭      persona.interests
  → [3] 접근성 감점      persona.accessibility · travelers
  → [4] 예산 감점        persona.budget
  → [5] 카테고리 균형    한 카테고리 25% 이하
  → [6] 관심사 커버리지  각 관심사 최소 1건, 상위 관심사는 3건까지
  → 최대 20건
```

**[6]을 [5]보다 나중에 하는 이유**: 균형을 맞추다 보면 특정 관심사가 0건이 되는 일이 생긴다. 마지막에 커버리지를 강제로 채워야 검증 V8이 통과한다.

| 기준 | 내용 |
|---|---|
| 총 개수 | **최대 20건.** 조건을 만족하는 후보가 적으면 실제 건수만 반환하며 0건은 `no_results` |
| 카테고리 균형 | 한 카테고리가 25% 초과 금지. 배분 예시는 `spec.md` 6.2.2 |
| 관심사 커버리지 | `persona.interests`를 각 1건 이상 우선 커버하고, 상위 관심사는 3건까지 배정한다. 20건 한도 때문에 전부 충족할 수 없으면 사용자 입력 순서를 우선한다 |
| 인기 편중 방지 | 유명 관광지만 40개면 큐레이션이 아니다. **로컬 장소를 30% 이상** 섞는다 |
| 지역 분산 | 한 동네에 몰리면 일정 생성 시 클러스터링이 무의미해진다. 3–6개 권역에 분산 |

### 4.3 `interestTags`와 정렬

| 항목 | 규칙 |
|---|---|
| `interestTags` | 이 장소가 어떤 관심사에 해당하는지. `persona.interests`에 없는 값도 넣어도 된다 |
| 배열 순서 | 관심사 일치 항목이 위로. 프론트 기본 정렬이 `추천순`이고 순서를 그대로 쓴다 |
| 프론트 표시 | `interestTags`가 `persona.interests`와 겹치면 리스트 우측에 별 배지 + 툴팁 `'역사·문화' 관심사와 맞아요` |

### 4.4 좌표 정확성 — 가장 중요한 항목

`spec.md` 6.2.2:

> *"각 장소는 실제 좌표를 사용한다. 지도에 찍었을 때 실제 위치와 맞아야 동선·이동시간이 그럴듯해진다. **좌표가 틀리면 경로 최적화와 검증 결과가 모두 이상해 보인다.**"*

| 왜 치명적인가 | 파급 |
|---|---|
| 이동시간 계산 | 직선거리 기반이므로 좌표가 틀리면 `TravelLeg.minutes`가 전부 틀린다 |
| 경로 최적화 | 최근접 이웃 알고리즘이 엉뚱한 순서를 만든다 |
| 검증 V2 | 이동 시간 실현성 판정이 무의미해진다 |
| 지도 | 마커가 바다에 찍힌다. 즉시 눈에 보이는 오류 |

**출력 직전 자체 검사** (§1.6의 [3] 계층)

```
□ lat ∈ [-90, 90], lng ∈ [-180, 180]
□ 도시 중심에서 50km 이내
□ 두 장소의 좌표가 완전히 동일하지 않다 (복사 실수)
□ 좌표가 (0, 0)이 아니다
```

### 4.5 영업시간

| 규칙 | 내용 |
|---|---|
| 7건 전부 | `weekday` 0–6이 각각 하나씩 (I-P2) |
| 휴관 | `open: null` + `close: null` |
| `closedWeekdays` | `openingHours`에서 파생. **두 값이 어긋나면 V1이 오판정한다** (I-P3) |
| `lastEntry` | 있으면 채운다. V1이 마지막 입장 시각을 확인한다 |
| 다양성 | 박물관 계열 일부에 실제 휴관일을 반영한다. 전부 연중무휴면 V1 검증이 아무것도 못 잡고, 검증 기능이 시시해진다 |

### 4.6 `accessibility`는 모르면 `null`

```json
"accessibility": { "wheelchairAccessible": true, "strollerFriendly": true, "manyStairs": null }
```

⛔ **추측해서 `true`/`false`를 넣지 않는다.** `spec.md` 3.14.3 "정직하게":

> *"없는 수치·후기·로고를 만들지 않는다. 데이터가 없으면 그 섹션을 다른 구조로 바꾼다."*

프론트는 `null`인 항목을 **표시하지 않는다**(모르는 걸 아는 척하지 않는다). V7도 `null`은 판정 대상에서 제외하고 근거에 `정보 없음`으로만 기록한다. 휠체어 사용자가 잘못된 `true`를 믿고 갔을 때의 피해를 생각하면, 빈 값이 훨씬 낫다.

### 4.7 도구 구성 제안

| 도구 | `label` | `resultLabel` |
|---|---|---|
| `search_places` | `{도시}` 장소 정보 수집 중 | `{n}곳 수집` |
| `filter_by_persona` | 여행 스타일 매칭 중 | `{n}곳 선별` |
| `fetch_details` | 소개 · 리뷰 · 사진 가져오는 중 | `{n}곳 상세 완료` |
| `check_hours` | 영업시간 확인 중 | `{n}곳 확인` |

### 4.8 `agentNote`

**절반 이하에만** 붙인다. 전부에 붙으면 노이즈가 된다. 페르소나와 연결된 것만.

| 좋은 예 | 나쁜 예 |
|---|---|
| `유아차 이동이 편하고 입장료가 없어 가족 여행 첫날에 적합해요` | `아름다운 사찰입니다` |
| `이른 아침에 가면 관광객이 적어 사진 찍기 좋아요` | `인기 있는 곳이에요` |
| `계단이 많아 유아차로는 어려울 수 있어요` | `방문을 권해요` |

세 번째 예처럼 **부정적 정보도 넣는다.** 그게 신뢰를 만든다.

## 5. `itineraryGenerate`

### 5.1 목표

선택한 장소들을 **이동이 적고 영업시간을 지키는 일자별 계획**으로 배치한다. 사용자는 이 결과를 수정할 수 있으므로 **완벽할 필요는 없지만, 명백한 오류는 없어야** 한다.

### 5.2 배치 알고리즘 권고

```
[1] 지역 클러스터링     좌표 기반. 3–6개 권역
[2] 권역 → 일자 배정    이동 최소화 + 항공 도착/출발 제약
[3] 일자 내 순서 결정   영업시간 + 최근접 이웃
[4] 시각 배정           페이스 기준 시작 시각부터 체류·이동 누적
[5] 식사 블록 삽입      점심 12–14시 / 저녁 18–20시
[6] 항공·숙소 항목      첫날/마지막날 + 체크인/체크아웃
[7] 초과 장소 → 미배치  unassignedPlaceIds
[8] 이동 구간 계산      TravelLeg 전부
[9] 불변식 검사         I-I1~I-I13
```

**[3]에서 영업시간을 고려하면 V1 충돌이 애초에 생기지 않는다.** 검증에서 잡히게 두지 말고 여기서 해결한다. `spec.md` 6.6.4의 추론 예시:

> *"도쿄 국립박물관은 월요일 휴관이라 Day 3으로 옮겼습니다."*

**페이스 설정** (`spec.md` 5.4)

| `pace` | 하루 장소 수 | 시작 | 종료 |
|---|---|---|---|
| `relaxed` | 2–3 | 10:00 | 19:00 |
| `balanced` | 3–4 | 09:00 | 20:00 |
| `packed` | 5–7 | 08:00 | 21:30 |

**첫날·마지막날 특례**

| 상황 | 처리 |
|---|---|
| 항공 도착 당일 | 도착 시각 + 입국·수하물 **60분** + 공항→시내 이동 이후에 첫 일정. 하루 장소 수를 1–2개 줄인다 |
| 항공 출발 당일 | 출발 − 체크인 **120분** − 시내→공항 이동 이전에 마지막 일정 종료 |
| 숙소 체크인 | `stay.checkIn` 시각 이후 (보통 15:00) |
| 숙소 체크아웃 | 마지막날 `stay.checkOut`(보통 11:00) 이후 일정이 있으면 **짐 보관 블록**(`kind: 'buffer'`, 제목 `숙소에 짐 맡기기`)을 넣는다 |

### 5.3 이동시간 계산

`spec.md` 15.2의 계수를 그대로 쓴다. 직선거리(haversine)에 우회 계수를 곱한다.

| 수단 | 계산 | 적용 조건 |
|---|---|---|
| 도보 | `거리 × 1.35 ÷ 80 m/분` + 2분 | 직선 1.2km 이하 |
| 대중교통 | `거리 × 1.25 ÷ 450 m/분` + 대기·환승 8분 | 0.8km 초과 |
| 택시 | `거리 × 1.4 ÷ 350 m/분` + 3분 | 항상 |
| 자전거 | `거리 × 1.3 ÷ 220 m/분` + 2분 | 5km 이하 |

| 규칙 | 내용 |
|---|---|
| 주 수단 | 도보 가능 거리면 도보, 아니면 `persona.transports` 중 가장 빠른 것 |
| `alternatives` | 1–2개. 프론트가 커넥터에 `· 🚇 6분`으로 병기한다 |
| 5분 반올림 | `Math.round(min / 5) * 5`. *"어설픈 정밀도가 오히려 신뢰를 떨어뜨린다"* |
| `polyline` | 선택. 두 점을 잇는 **3점 꺾은선**(중간점을 수직으로 거리의 8% 이동)이 직선보다 자연스럽다 |
| `note` | `지하철 1회 환승` 등. 있으면 유용 |

### 5.4 하루 테마 제목

`ItineraryDay.title`은 그 날의 장소들에서 **지역명 1–2개**를 뽑아 만든다. 20자 이내.

| 좋은 예 | 나쁜 예 |
|---|---|
| `아사쿠사 & 스카이트리` | `첫째 날` (날짜는 이미 표시된다) |
| `시부야 & 하라주쿠` | `도쿄 관광` (전부 도쿄다) |
| `우에노 & 야네센` | `문화와 역사가 어우러진 하루` (길고 공허하다) |

### 5.5 `agentReason` — 배치 이유

각 장소 항목에 **40자 이내** 한 줄. 이 필드가 "AI가 생각해서 배치했다"는 인상을 만든다.

| 좋은 예 | 나쁜 예 |
|---|---|
| `오후 햇빛이 좋아요` | `좋은 장소입니다` |
| `월요일 휴관이라 이 날로 옮겼어요` | `일정에 맞춰 배치했어요` |
| `공항에서 가까워 도착 첫날에 넣었어요` | `추천 장소예요` |
| `저녁 야경을 보기 좋은 시간이에요` | `인기가 많아요` |

시각과 순서에 대한 **구체적 근거**만 쓴다. 장소 자체의 매력은 `Place.agentNote`가 이미 담당한다.

### 5.6 미배치 장소

| 규칙 | 내용 |
|---|---|
| 언제 생기는가 | 선택 장소가 페이스 대비 많을 때. 무리하게 밀어넣지 말고 미배치로 둔다 |
| ⛔ 금지 | 조용히 버리기. 사용자가 고른 장소가 사라진 것처럼 보인다 (I-I2) |
| 프론트 동작 | 하단 미배치 패널에 표시 + 드래그로 배치 가능 |
| 추론 언급 | 미배치가 생겼으면 `thought`에서 이유를 말한다. `선택하신 12곳 중 10곳을 배치했어요. 남은 2곳은 아래에서 원하는 날에 넣을 수 있습니다.` |

### 5.7 도구 구성 제안

| 도구 | `label` | `resultLabel` |
|---|---|---|
| `cluster_by_area` | 지역별로 묶는 중 | `{n}개 권역으로 분류` |
| `check_opening_hours` | 요일별 영업시간 대조 중 | `{n}건 조정` |
| `estimate_travel` | 이동 시간 계산 중 | `{n}개 구간 계산` |
| `assign_meals` | 식사 시간 배치 중 | `{n}개 식사 배치` |

### 5.8 `partial` 방출이 이 작업의 핵심 연출

`spec.md` 6.6.4:

> *"`partial` 이벤트마다 해당 일자 섹션이 `slide-up` 200ms로 등장하고, 그 안의 항목은 60ms stagger로 나타난다. 동시에 지도 마커도 같은 순서로 `marker-pop`한다. 이 순간이 이 앱에서 가장 인상적인 장면이므로 **절대 스피너로 대체하지 않는다.**"*

| 규칙 | 내용 |
|---|---|
| 단위 | `ItineraryDay` 1개 (항목·이동구간 전부 포함된 완성된 하루) |
| 순서 | `dayIndex` 0, 1, 2… 순서대로 |
| 간격 | 300–400ms |
| 사이에 `thought` | Day 1 방출 후 `첫날은 11:20 도착이라 공항 이동과 체크인을 고려해 가볍게 잡았어요` 같은 문장을 끼우면 리듬이 살아난다 |

⛔ 전체 일정을 다 만든 뒤 `done` 하나로 보내면 계약은 지켜지지만 **이 제품의 가장 좋은 장면이 사라진다.**

## 6. `itineraryVerify`

가장 복잡하고, 이 제품의 차별점이 가장 뚜렷한 작업이다.

### 6.1 규칙 소유권

🔶 [`contract.md` 부록 A6](./contract.md#부록-a-specmd-정합성-메모)

`spec.md` 9장은 규칙 V1–V10을 `src/lib/verify/rules.ts`(프론트)에 두는 것으로 설계되어 있다. 이는 **목 모드 기준**이다.

| 모드 | 규칙 판정 위치 | 이유 |
|---|---|---|
| `mock` | 프론트 (`src/lib/verify/rules.ts`) | 백엔드 없이 동작해야 한다 |
| `live` | **에이전트 서버** | 판정 근거와 서술이 함께 나와야 자연스럽다 |

**두 구현이 같은 결론을 내야 한다.** `spec.md` 9.2가 양쪽의 공통 사양이다. 판정이 갈리면 `mock` ↔ `live` 전환 시 사용자가 다른 결과를 본다.

> 프론트의 규칙 구현을 **참조 구현(reference implementation)** 으로 삼는 것을 권한다. 같은 입력으로 양쪽을 돌려 `severity`가 일치하는지 비교하는 것이 가장 확실한 검증이다. → [`integration.md` §5.3](./integration.md#53-규칙-일치-테스트)

### 6.2 하이브리드 구조

```
VerifyInput
   ↓
[1] 규칙 엔진 (결정론)        V1–V10 판정. severity · targetRefs · 수치 근거
   ↓  구조화된 판정 결과
[2] LLM (서술)               issue.title/detail · evidence 문장화 · autoFix.summary 이유
   ↓
[3] 자동 수정 생성 (결정론)   ItineraryChange[] 계산 + 적용 가능성 검사
   ↓
[4] 불변식 검사              I-V1~I-V10
   ↓
check_update × 20+ · thought × 5–7 · done
```

**[3]이 결정론이어야 하는 이유**: 자동 수정은 프론트가 **실제로 일정에 적용**한다. LLM이 "Day 3 10:30으로"라고 말했는데 그 시각에 다른 항목이 있으면 일정이 깨진다. 제안을 만든 뒤 **적용 시뮬레이션을 돌려** 새 충돌이 생기지 않는지 확인하고, 생기면 그 제안을 버리고 `autoFix: null`로 둔다.

### 6.3 규칙별 구현 메모

판정 로직 전문은 [`spec.md` 9.2](../spec.md#92-규칙-상세)가 원본이다. 여기서는 **틀리기 쉬운 지점**만 적는다.

| 규칙 | 주의 |
|---|---|
| **V1** 영업시간 | `weekday`는 **0 = 일요일**. `date`에서 요일을 계산할 때 로컬 타임존 영향을 받지 않게 한다(문자열 파싱 권고). `closedWeekdays` 캐시와 `openingHours`가 어긋나면 오판정 |
| **V2** 이동 시간 | `여유 = 다음 시작 − (현재 시작 + 체류) − 이동`. 음수면 `conflict`, 0–10분이면 `warning`. 단일 구간 90분 초과도 `warning` |
| **V3** 항공 여유 | 도착: 입국·수하물 **60분** + 공항→시내 이동. 출발: 체크인 **120분** + 시내→공항. 이 상수를 근거에 명시한다 |
| **V4** 숙소 | 체크인 항목이 `stay.checkIn`보다 이르면 `warning`. 체크아웃 후 일정이 있는데 짐 보관 블록이 없으면 `warning` |
| **V5** 하루 일정량 | `conflict` 없음(물리적으로 불가능한 게 아니다). 이동/활동 비율 40% 초과도 `warning` |
| **V6** 예산 | 식사 **1인 1식 15,000원 × 하루 2식**, 교통 **하루 8,000원/인**. 추정임을 근거에 명시. `budget.includesFlight/Stay`를 반영 |
| **V7** 접근성 | `null`은 판정 제외. 근거에 `정보 없음`으로만 기록. `conflict` 없음(본인 판단 여지) |
| **V8** 관심사 | 미반영 관심사 + 한 카테고리 60% 초과 편중 |
| **V9** 예약 | 일정을 바꾸지 않는다. `changes: []` + `kind: 'add-todo'`. 프론트는 diff 없이 즉시 적용하고 버튼 라벨도 `[준비물에 추가하기]` |
| **V10** 시즌 | `SEASON_NOTES` 테이블 (`spec.md` 9.2 V10). 하루 야외 비율 70% 초과 시 `warning`. `changes: []` |

**모든 규칙 공통**

| 항목 | 규칙 |
|---|---|
| 10개 전부 실행 | 건너뛰어도 `severity: 'skipped'`로 `done` 이벤트를 보낸다 (I-V1) |
| 순서 | V1 → V10. 내부 병렬 실행은 자유, **이벤트는 순차** |
| `evidence` | 규칙당 2–4줄. 수치를 반드시 포함. 접두 규약은 [`contract.md` §4.6](./contract.md#46-check_update-) |
| `targetRefs` | 검사한 대상. 이슈가 없어도 채운다(무엇을 봤는지 보여준다) |

### 6.4 근거의 품질이 검증의 설득력이다

`spec.md` 1.2:

> *"별도 검증 에이전트가 10개 규칙으로 일정을 점검하고, 문제를 자동 수정까지 제안한다."*

사용자가 "이 검증을 믿을 수 있나"를 판단하는 근거는 **`evidence` 배열 하나뿐**이다.

| 좋은 근거 (V1) | 나쁜 근거 |
|---|---|
| `영업시간: 화–일 09:30–17:00, 월요일 휴관` | `영업시간을 확인했습니다` |
| `6월 15일은 월요일` | `날짜가 맞지 않습니다` |
| `방문 예정 11:00 · 체류 2시간 30분` | `시간 문제가 있습니다` |

| 좋은 근거 (V2) | 나쁜 근거 |
|---|---|
| `센소지 15:00–16:30 → 도쿄 스카이트리 17:00` | `이동 시간이 부족합니다` |
| `이동 도보 12분 + 대기` | `거리가 멉니다` |
| `여유 18분` | `촉박합니다` |

**패턴**: `사실 → 수치 → 판정`. 사용자가 스스로 검산할 수 있으면 신뢰한다.

### 6.5 자동 수정 제안

| 규칙 | 내용 |
|---|---|
| 실현 가능성 | 제안을 적용한 결과를 **시뮬레이션**해 새 충돌이 없는지 확인한다. 없으면 `autoFix: null` |
| `locked` 항목 | ⛔ 위치·시각을 바꾸지 않는다. 사용자가 고정한 것이다 |
| `kind: 'flight'` / `'stay-*'` | ⛔ 위치를 바꾸지 않는다 |
| 연쇄 영향 | `changes`에 파생 변경까지 모두 담는다. 프론트가 **함께 바뀌는 것** 섹션에 표시한다 |
| `impact` | 20자 이내 정량 표현. `이동시간 +4분` · `Day 3 활동 2시간 감소` |
| `payload` | [`contract.md` 부록 B](./contract.md#부록-b-itinerarychangepayload-스키마-제안) 스키마 🔶 |
| `beforeLabel` / `afterLabel` | 사람이 읽는 diff. `payload`와 **내용이 일치**해야 한다 |

**제안 이유가 좋은 예**

> `Day 3(6/14 토) 10:30으로 옮기기`
> `Day 3에 우에노 공원이 있어 같은 지역이라 이동이 늘지 않아요.`
> `이동시간 +4분`

"왜 이 날인지"를 말한다. 그냥 `다른 날로 옮기기`는 사용자가 판단할 근거를 주지 않는다.

### 6.6 이벤트 리듬

`spec.md` 6.6.5의 구조를 따른다. 검사만 10번 연속하면 리스트가 기계적으로 채워질 뿐이다. **문제를 찾은 규칙 뒤에는 추론 문장을 붙인다.**

```
status   "일정을 검증할게요"
thought  "5일 일정, 총 17개 방문지를 10개 항목으로 점검합니다."
check    V1 running → evidence 3줄 점진 추가 → done (conflict 1)
thought  "Day 4의 도쿄 국립박물관이 월요일 휴관입니다. 근처 대안이나 다른 날 이동을 제안할게요."
check    V2 running → done (warning 1)
thought  "Day 3의 이동 여유가 8분입니다. 다음 일정을 20분 미루면 여유가 생겨요."
check    V3 → done (pass)      ← 통과한 규칙은 문장 없이 넘어간다
check    V4 → done (pass)
check    V5 → done (warning 1)
thought  "Day 3은 활동 시간이 11시간 20분으로 '적당히' 페이스보다 깁니다."
check    V6 → done (skipped)
check    V7 → done (pass)
check    V8 → done (pass)
check    V9 → done (warning 1)
check    V10 → done (pass)
thought  "검증을 마쳤어요. 충돌 1건, 주의 3건을 찾았습니다. 자동 수정을 적용하면 대부분 해결됩니다."
done     VerificationReport
```

| 규칙 | 내용 |
|---|---|
| 문장을 붙이는 곳 | 문제를 찾은 규칙 뒤 + 시작 + 종료 |
| 통과한 규칙 | 문장 없이 넘어간다. 전부 설명하면 소음이 된다 |
| 검사 간 간격 | 800–1,300ms. 총 11–15초 |

## `cityInfo`

### 목표

선택한 도시의 여행 준비에 필요한 최신 실용 정보를 웹에서 조사해 **출처가 있는 단일 `CityInfo` 객체**로 제공한다. 장소 후보를 반환하는 `placeDiscovery`와 달리 도시 개요, 날씨, 교통, 안전, 에티켓, 준비 팁을 다룬다.

### 데이터 수집 순서

```text
[1] cityId로 도시 식별
  → [2] 공식 관광청·정부·교통기관 우선 검색
  → [3] dateRange가 있으면 해당 시기 날씨·준비 정보 조사
  → [4] 출처 간 핵심 사실 교차 확인
  → [5] 짧고 실행 가능한 한국어로 정리
  → [6] 출처와 조회 시각을 붙여 CityInfo 반환
```

| 영역 | 원칙 |
|---|---|
| 도시 기본 정보 | timezone·통화·언어는 신뢰할 수 있는 출처로 확인하고 추측하지 않는다 |
| 날씨 | 일기예보와 평년 기후를 구분한다. 여행 날짜가 예보 가능 범위 밖이면 계절 경향이라고 명시한다 |
| 교통 | 공항 이동, 주요 대중교통, 교통카드·패스 중 실제 여행에 필요한 내용만 요약한다 |
| 안전 | 과장된 위험 표현을 피하고 공식 여행 경보·현지 기관 정보를 우선한다 |
| 에티켓 | 여행자가 행동으로 옮길 수 있는 짧은 팁으로 작성한다 |
| 출처 | 최소 1건. 응급번호·여행 경보처럼 중요한 사실은 공식 출처를 우선한다 |

### 결정론 코드와 LLM의 경계

| 결정론 코드 | LLM 허용 |
|---|---|
| 입력 검증, URL·조회 시각 기록, 중복 출처 제거, 필수 필드 검증 | 검색 질의 생성, 여러 출처 요약, 한국어 설명 작성 |
| `cityId` 일치, ISO 통화·timestamp 형식 검사 | 출처 간 차이 설명, 실용 팁 우선순위 지정 |

검색 결과를 찾지 못했거나 신뢰할 출처를 확보하지 못하면 내용을 만들어내지 않고 `error(no_results)`로 종료한다. 웹 페이지의 문장을 길게 복사하지 않고 사실만 재서술한다.

### 이벤트 리듬

```text
status     "도시 정보를 확인하고 있어요"
thought    "도쿄의 교통과 여행 시기 정보를 공식 출처부터 확인합니다."
tool_call  web_search
 tool_result 출처 수
thought    "날씨, 교통, 안전 정보를 교차 확인해 여행 준비 팁으로 정리합니다."
done       CityInfo
```

`partial`은 사용하지 않는다. 완성된 정보와 출처가 함께 있어야 의미가 있으므로 최종 객체를 한 번에 반환한다.

## 7. 품질 평가

### 7.1 골든 케이스

아래 5개 입력으로 매번 돌려보고 눈으로 확인한다. [`fixtures/inputs.json`](./fixtures/inputs.json)에 넣어둔다.

| # | 케이스 | 무엇을 보는가 |
|---|---|---|
| G1 | 도쿄 4박5일 · 연인 · `balanced` · 맛집+자연 | 기본 동작. 모든 작업의 해피패스 |
| G2 | 도쿄 4박5일 · 가족(6세 아동) · `relaxed` · 유아차 | 접근성 반영. 계단 많은 곳이 뒤로 밀리는가 |
| G3 | 파리 7박8일 · 혼자 · `packed` · 미술관 편중 | 카테고리 편중 시 V8이 잡는가 |
| G4 | 방콕 2박3일 · 친구 · 예산 60만원 | 예산 제약 반영. V6이 동작하는가 |
| G5 | 도쿄 4박5일 · 항공·숙소 미선택 | V3·V4가 `skipped`로 정상 처리되는가 |

### 7.2 루브릭

작업 하나를 5개 축으로 1–5점 채점한다. **3점 미만 항목이 있으면 릴리스하지 않는다.**

| 축 | 1점 | 3점 | 5점 |
|---|---|---|---|
| **정확성** | 좌표·시각·계산이 틀림 | 계산은 맞지만 근거가 얕음 | 전부 정확하고 검산 가능 |
| **페르소나 반영** | 입력과 무관한 결과 | 관심사만 반영 | 관심사·페이스·접근성·`freeNote`까지 |
| **추론 설득력** | 도구 이름 나열 | 무엇을 했는지 서술 | **왜 그렇게 판단했는지** 서술 |
| **카피 품질** | 영문 혼재·기계 번역체 | 어색하지만 이해 가능 | `spec.md` 7장 톤과 구분 안 됨 |
| **완결성** | 필수 필드 누락 | 채워졌지만 빈약 | 선택 필드까지 의미 있게 채움 |

### 7.3 빠른 자체 점검

```
□ 이 결과를 처음 보는 사람이 "AI가 나를 위해 골랐다"고 느끼는가
□ 추론 문장에서 내 입력(관심사·페이스·메모)이 인용되는가
□ 근거의 숫자를 내가 손으로 검산할 수 있는가
□ 지도에 찍힌 마커가 실제 위치와 맞는가
□ 검증이 실제로 문제를 하나라도 잡아내는가 (전부 통과면 목데이터에 함정이 없다)
□ 자동 수정을 적용하면 그 문제가 정말 해결되는가
□ 화면에 영문·이모지·마크다운 기호가 노출되지 않는가
□ 최대 20곳이 유명 관광지에만 편중되지 않았는가
```

## 8. 실패와 저품질 대응

### 8.1 LLM 실패

| 상황 | 대응 |
|---|---|
| JSON 파싱 실패 | 1회 재시도 → 실패 시 `error`(`agent_failed`) |
| 열거형 벗어난 값 | 출력 직전 검증에서 **가장 가까운 허용값으로 보정**하거나 그 항목 제외. ⛔ 그대로 보내지 않는다 |
| 존재하지 않는 `placeId` 참조 | 그 항목 제외. 심하면 `agent_failed` |
| 길이 초과 문장 | 서버에서 잘라서 보낸다(프론트가 말줄임하지만 레이아웃이 밀릴 수 있다) |
| 쿼터 초과 | `error`(`rate_limit`, `retryable: true`) |
| 타임아웃 임박 | 지금까지의 결과로 `done`. LLM 서술이 없으면 **템플릿 문장으로 폴백** |

### 8.2 서술 폴백

LLM이 실패해도 **결정론 계층의 결과는 살아 있다.** 서술만 템플릿으로 대체해 결과를 살린다.

| 필드 | 폴백 템플릿 |
|---|---|
| `done.summary` | `{n}개 항공권을 찾았어요.` |
| `Place.agentNote` | 생략 (선택 필드) |
| `agentReason` | 생략 (선택 필드) |
| `issue.title` | `{장소명} · {규칙 라벨} 문제가 있습니다` |
| `issue.detail` | `evidence`의 첫 줄을 그대로 |
| `ItineraryDay.title` | 생략 (선택 필드) |

> 서술이 조금 딱딱해지는 것과, 화면이 아예 안 뜨는 것은 전혀 다른 문제다. **결과를 살리는 쪽을 택한다.**

### 8.3 결과 부족

| 상황 | 대응 |
|---|---|
| 0건 | `error`(`no_results`) + `message`에 원인 조건 명시 |
| 목표 미달 (예: 장소 18건) | `done`. `summary`에 `조건에 맞는 곳이 18곳이에요` |
| 카테고리 균형 실패 | `done`. 검증 V8이 나중에 잡는다 |
| 관심사 커버리지 실패 | `done`. `thought`에서 언급: `'휴양·온천'에 해당하는 곳은 이 도시에서 찾지 못했어요` |

### 8.4 데모 안정성

발표 중 실패는 복구할 시간이 없다.

| 대비 | 방법 |
|---|---|
| 응답 캐시 | 골든 케이스 5개의 결과를 캐시해 둔다. 같은 입력 → 즉시 응답 |
| 목 폴백 | 3회 실패 시 프론트가 목 데이터로 전환한다 (`spec.md` 6.8). 이 경로를 **끄지 않는다** |
| 리허설 | 발표 경로를 3회 이상 실행해 본다. 첫 실행에서만 실패하는 문제가 자주 있다 |
| 네트워크 | 외부 API 의존을 최소화한다. 로컬 데이터 + LLM 1회가 가장 안전하다 |
